# StoreKit 1 catalog and delivery repair

## Confirmed cause

On November 17, 2026, the owner's Wallet showed 1,200 coins and nine unavailable offers. Logs at 14:17:46–14:17:51 identified `im.seex.sao2`, initialized StoreKit with server Sandbox, requested Apple's sandbox catalog, and returned no eligible products. A separate receipt synchronization warning said No active account; this does not establish the cause of Apple's catalog availability.

Xcode's Run options then showed the configured file was missing at `/Users/apple/Desktop/Vava/Configuration/VavaCoins.storekit`. The actual file is under `/Users/apple/Desktop/Vava/Vava/Configuration/`. The shared scheme had `../../Configuration/VavaCoins.storekit`, using XcodeGen's non-workspace default. Selecting the actual file in Xcode generated `../Configuration/VavaCoins.storekit`. The generator now sets `schemePathPrefix: "../"`, as required for workspaces. The source catalog and fixture contain the same nine product IDs.

A second defect treated an empty catalog as a successful refresh. The focused regression failed before the change with `An empty StoreKit catalog must not report a successful refresh.` (`/tmp/vava-catalog-red.xcresult`, one test, one expected failure). The native wallet now reports idle/loading/ready/partial/unavailable/failed states, rejects empty results and request failures, and retains available offers from partial responses. The H5 page clears a previous refresh notice and only reports Updated for a ready catalog.

## StoreKit 1 migration

The owner explicitly requested StoreKit 1. Production code uses SKProductsRequest, SKProduct, SKMutablePayment, SKPaymentQueue and SKReceiptRefreshRequest. It does not use StoreKit 2 Product, Transaction, updates, unfinished sequences or purchase APIs. Retained request delegates resolve once on completion, cancellation or timeout. Queue observation begins when the local account wallet opens; unfinished queue transactions are retried on login and explicit refresh. Stopping a wallet cancels pending catalog work and releases checkout continuations. An already credited callback cannot complete a newer checkout. After credit, checkout waits for SKPaymentQueue to acknowledge transaction removal, with a bounded wait; an unsettled purchased transaction prevents a new checkout. This handles the asynchronous finishTransaction boundary rather than assuming its return means the queue is ready for another payment.

Purchases retain the existing per-account files, serialized ledger shape, coin mappings and `apple:<transactionIdentifier>` deduplication keys. No balance or history migration/reset is required. Canceled, failed or deferred payments do not credit. Credit is published after atomic persistence; failed delivery remains unfinished for retry. The account must match the queue's applicationUsername. Legacy receipts do not provide the previous StoreKit 2 signed appAccountToken guarantee, so missing usernames are rejected rather than assigned to the current account. Recovery of a pending transaction created by the previous API without an available username is not yet verified.

TPInAppReceipt 4.0.2 validates PKCS#7 signatures, certificate trust, metadata and device hash where supported. The app additionally checks the exact bundle, environment, transaction, product, quantity and cancellation status. Local ledgers accept only Xcode receipts; Apple ledgers reject Xcode receipts. Release cannot select the local ledger. A duplicate already durably committed to this account is finished without requiring a consumable receipt entry that may disappear after finishing. After asynchronous verification the ledger is checked again to prevent concurrent duplicate credit.

This remains a device-local wallet. There is no new backend, server-authoritative balance, remote receipt endpoint, refund reconciliation or cross-device consumable restoration. StoreKit 1 is Apple's deprecated original API, retained here at the owner's explicit request.

## Dependencies and notices

`Vava.xcworkspace/xcshareddata/swiftpm/Package.resolved` locks TPInAppReceipt and Apple's swift-asn1, swift-certificates and swift-crypto dependencies. Their upstream license and notice files are included under `Assets/Licenses` and copied into the application bundle. The verification library includes a public StoreKit Test certificate; the application environment guard prevents its use for Apple-ledger credit. The actual StoreKit product fixture remains outside app resources.

## Verification

The first StoreKit 1 run passed two tests (empty catalog/recovery and H5 pages/payment). A subsequent native test exposed an old purchased callback incorrectly completing the next canceled checkout. Ignoring the duplicate result alone exposed a queue-removal wait, and that focused run was stopped without a passing claim. After waiting for the actual removedTransactions acknowledgement, the native purchase/cancellation/12 concurrent duplicates/reopen test passed (one test, zero failures, 2.214 seconds; `/tmp/vava-sk1-queue-ack.xcresult`). The final combined run passed **3 tests, 0 failures, 0 skipped**, with 31.887 seconds of test execution (`/tmp/vava-sk1-matrix.xcresult`). It used a fresh isolated application container on **Vava UI Acceptance**, iPhone 17 Pro, **iOS 26.0.1**, built using Xcode 26.0.1. Coverage includes an empty catalog, partial catalog, full recovery, all H5 page navigation, successful credit, cancellation, twelve concurrent duplicate callbacks and reopening the wallet. The earlier November 16 StoreKit 2 results are not StoreKit 1 acceptance evidence.

The original application was then built and launched from the corrected Xcode Run scheme. Its installed local H5 archive matches the current workspace archive. The first read-only UI check confirmed all nine enabled price buttons and the Me wallet label of 1,200 coins, then failed because the test expected one combined balance accessibility element. The actual H5 tree exposes `1,200` and `coins` as separate text elements. This was a test-selector correction, not an application balance defect. After correcting the selector against the actual hierarchy, the final UI run passed **1 test, 0 failures**, in 18.656 seconds (`/tmp/vava-sk1-owner-ui/results3.xcresult`). All nine price buttons are enabled and the wallet displays 1,200 coins. The passing test source and screenshot are saved with the evidence.

After the original-app inspection, the wallet and local-library JSON file set and SHA-256 hashes exactly match the pre-repair baseline: two files, unchanged. The original wallet remains at **1,200 coins with two entries**. All purchase/cancellation/replay operations used isolated acceptance bundles; the original application was only used to inspect prices and balance.

Both TypeScript checks passed, the local H5 archive was repackaged, and static validation passed **615 checks**. Durable result summaries, catalog/credit screenshots and the data-preservation comparison are under `Docs/Evidence/StoreKit1/`.

These are **local StoreKit Test** results. Apple sandbox catalog availability, production purchases, real-device receipt hashing, deferred approval, refund handling and pending transactions originating in the previous StoreKit 2 implementation were not accepted by this run.
